# AI와 함께 만드는 1인 게임 — Wind Courier의 컨셉 설계부터 Steam 출시까지

작성: 2026-10-03. 강의 시간: 120분(휴식 5분, 질의응답 10분 포함).

## 강의의 전제

Wind Courier(바람 배달부) 한 작품을 따라가며, 1인 개발자가 AI를 기획·구현·콘텐츠 제작·검증·출시 준비에 어떻게 연결하는지 설명한다. 대상은 게임 제작에 관심 있는 예비·초급 1인 개발자다. 엔진 코드를 읽지 않아도 흐름을 이해할 수 있도록 결과 화면과 작업 전후 비교를 중심으로 진행한다.

수강 후에는 자신의 게임을 한 문장으로 정의하고, 첫 검증 범위를 정하고, AI 작업 요청에 완료 조건을 붙이고, 출시까지 남은 일을 정리할 수 있어야 한다.

핵심 메시지: **AI가 만든 결과를 선택하고, 게임 안에서 확인하고, 완성 기준에 맞춰 연결하는 것이 1인 개발자의 일이다.**

이 문서의 실제 사례는 저장소에 남은 개발 기록을 기준으로 한다. 이번 강의안 작성 과정에서 게임 실행이나 재검증을 하지는 않았다. Steam 출시 완료·심사 통과·판매 실적은 확인되지 않았으므로, 출시 부분은 앞으로 수행할 절차로 설명한다. 강의일에 출시가 끝났다면 해당 구간을 실제 제출·출시 기록으로 교체한다. 아래 프롬프트는 강의용으로 재구성한 예시이며 과거 대화의 원문이 아니다.

## 1. 오프닝 — 혼자 만드는 Wind Courier (8분)

진행: 플레이 영상 2분 → 게임 소개 2분 → 개발자의 역할 3분 → 오늘의 흐름 1분.

첫 화면에는 현재 빌드의 이륙, 상승기류, 저공 우편 투하, 착륙 전달, 편지 읽기를 짧게 연결한 영상을 보여준다. 촬영되지 않은 장면은 실제 촬영 후 넣는다.

발표 멘트:

> “이 게임은 작은 우편 비행기로 바람을 읽고 편지를 전하는 Wind Courier입니다. 오늘은 이 화면이 만들어지기까지 어떤 판단이 필요했는지 따라가 보겠습니다. 컨셉을 정하고, 날 수 있게 만들고, 편지를 배달하고, 다른 사람의 컴퓨터에서 실행되는 제품으로 만드는 과정입니다.”

기획자, 프로그래머, 아트 디렉터, 테스터, 출시 담당자의 역할을 한 사람이 오간다는 점을 설명한다. AI에는 초안·구현·변환·반복 확인을 맡기고, 개발자는 경험의 방향·채택 여부·직접 플레이·출시 판단을 맡는다.

게임 소개에 사용할 정보:

- 1920년대 유럽풍 가상 지역, 저속 비행 어드벤처.
- 열여섯 살 우편 비행사 리브, 돌아오지 않은 아버지의 미배달 우편 가방.
- 핵심 질문: “오늘의 바람을 보고, 어떤 길로 갈 것인가?”
- Unreal Engine 5 기반, PC/Steam을 목표로 개발.
- 메인 이야기 목표 분량 약 1시간 30분. 실제 모든 플레이어의 완료 시간을 보장하는 수치는 아니다.

화면에는 ‘설계’, ‘구현 기록 있음’, ‘사람 확인 남음’, ‘출시 절차 예정’을 구분해 표시한다.

## 2. 컨셉 — 바람과 편지를 게임의 규칙으로 (15분)

진행: 컨셉 4분 → 범위 결정 4분 → AI 요청 사례 4분 → 청중 활동 3분.

### 감정을 행동으로 바꾸기

Wind Courier의 정서는 “상실을 안고 있지만, 하늘은 여전히 아름답다”다. 이 문장을 플레이어 행동으로 내려보낸다.

| 컨셉의 요소 | 플레이어가 실제로 하는 일 | 제작할 대상 |
|---|---|---|
| 바람을 읽는다 | 기류를 찾고 진입해 고도를 얻는다 | 기류 규칙, 바람의 시각 단서, 비행 피드백 |
| 편지를 전한다 | 낮게 접근해 우편을 투하하거나 착륙한다 | 투하 조건, 착륙 구역, 수취인 반응 |
| 사람과 연결된다 | 기다리던 편지와 답장을 읽는다 | 편지, 짧은 대사, 전달 후 변화 |
| 하루를 살아간다 | 노선을 고르고 비행 후 돌아와 쉰다 | 아침 카운터, 귀환, 저녁, 저장 |

발표 멘트:

> “AI에게 세계관을 확장해 달라고 하면 많은 아이디어를 얻을 수 있습니다. 그 아이디어를 채택할 때마다 모델, 화면, 코드, 테스트도 늘어납니다. 저는 플레이어가 반복할 행동과 그 행동에 필요한 범위부터 정해야 합니다.”

### 실제 사례: 분량을 줄이는 판단

컨셉 문서에는 12시간·30일을 전제로 한 이전 장편안을 채택하지 않고, 2~3시간의 짧고 완결된 게임을 목표로 삼은 기록이 있다. 이후 2026-09-25에는 메인 이야기 목표를 약 1시간 30분으로 조정했다. 당시 기록은 비행만 최단 약 30분, 선택 노선·서랍 편지를 더하면 약 1시간으로 정리되어 있다. 이는 당시 빌드와 측정 조건의 결과다.

설명할 판단: 배달 횟수를 늘리는 대신 저녁·아침 장면과 편지 읽기로 이야기의 밀도를 더한다. 세 기체와 전체 서사를 한 번에 제작하지 않고 최소 비행과 첫 배달부터 검증한다.

### 강의용 프롬프트

```text
Wind Courier는 바람을 읽으며 편지를 배달하는 저속 비행 어드벤처다.
핵심 감정은 ‘상실을 안고 있지만, 하늘은 여전히 아름답다’이다.
1인 개발이며, 짧고 완결된 게임을 목표로 한다.

현재 컨셉 문서를 읽고 다음을 한 장으로 정리해 줘.
1. 플레이어가 반복할 핵심 행동
2. 첫 프로토타입에서 확인할 재미 한 가지
3. 반드시 필요한 기능과 나중으로 미룰 기능
4. 확정된 결정과 아직 검증하지 않은 가정
새로운 기능을 제안하면 추가 제작·검증 작업도 함께 적어 줘.
```

청중 활동 3분: Wind Courier의 첫 프로토타입에 넣을 항목 3개를 고르게 한다. 후보는 비행, 기류, 우편 투하, 기체 3대, 전체 이야기, 정교한 마을이다. 비행·기류·투하를 선택한 이유를 설명하며 첫 검증 범위로 연결한다.

산출물: 한 문장 컨셉, 핵심 반복 행동, 이번에 만들 범위, 미룬 목록.

## 3. 프로토타입 — 비행과 첫 배달 만들기 (20분)

진행: 첫 반복 행동 4분 → 작업 요청 설계 5분 → 준비된 시연 7분 → 기록 관리 4분.

첫 구현 흐름을 ‘기류 탐색 → 상승 → 활공 → 저공 투하 → 고도 회복’으로 제시한다. 지형과 기체는 임시 표현이어도 이 흐름은 직접 조작할 수 있어야 한다.

### AI에게 맡길 수 있는 크기로 나누기

작업 순서는 최소 비행, 기류 진입·이탈, 투하 성공·실패, 완료 상태, 기록 저장으로 나눈다. 각 작업은 확인 방법을 갖는다.

| 작업 | 완료 조건 예시 |
|---|---|
| 기류 | 범위 안에서 상승 효과가 있고, 벗어나면 사라진다 |
| 투하 | 조건 안에서만 성공하고 실패하면 편지가 남는다 |
| 완료 처리 | 성공 직후 버튼을 다시 눌러도 중복 완료되지 않는다 |
| 측정 | 투하와 고도 회복 시점이 기록된다 |

```text
Wind Courier의 기존 비행·배달 코드와 관련 기획을 먼저 읽어 줘.
이번 작업은 우편 투하의 성공·실패 처리다.

기획에 정해진 조건 밖에서 투하하면 편지를 보존하고,
조건 안에서 투하하면 한 번만 배달 완료로 처리해 줘.
완료 직후 다시 입력해도 보상이 중복되지 않아야 한다.

관련 부분만 수정하고 빌드와 해당 자동 검사를 실행해 줘.
변경한 행동, 실행한 검사, 아직 직접 플레이해야 할 항목을 알려 줘.
기획에 없는 수치는 임의로 확정하지 말고 가정으로 표시해 줘.
```

### 7분 시연 구성

1. 1분: 해당 규칙과 완료 조건을 보여준다.
2. 2분: 조건 밖 투하 → 편지 보존 → 재접근 → 정상 투하 영상을 보여준다.
3. 2분: 관련 코드 변경 일부와 자동 검사 결과를 연결해 보여준다.
4. 2분: 사람이 느끼는 조작감과 화면 인지는 별도로 확인한다고 설명한다.

빌드와 생성 대기 시간을 줄이기 위해 결과가 준비된 녹화 시연을 기본으로 한다. 과거 기록의 재현임을 표시하고, 라이브 실행은 준비된 짧은 동작 확인만 한다.

### AI와 오래 작업하려면 남겨야 하는 것

Wind Courier에는 컨셉, 시놉시스, 비행·코어 루프, 게임플레이, 미결 사항, 측정 기록이 나뉘어 있다. 규칙의 원문은 담당 문서에 두고 다른 문서는 링크한다. AI에게 작업을 요청할 때 관련 문서·현재 상태·이번 목표를 함께 준다.

작업 흐름: 작은 변경 → 빌드 → 필요한 검사 → 플레이 확인 → 결정 기록 → Git으로 변경 이력 보존. 코드와 큰 바이너리 에셋은 저장·백업 방식을 구분해 관리한다.

발표 멘트:

> “AI와의 대화에서 결정한 내용도 다음 작업의 입력이 되어야 합니다. 무엇이 확정됐고 무엇을 아직 확인하지 않았는지 파일에 남기면, 다음 작업에서 같은 논의를 반복하는 일을 줄일 수 있습니다.”

## 4. 아트·서사·사운드 — 같은 세계로 통일하기 (15분)

진행: 기체·인물 5분 → 바람 표현 4분 → 편지·소리 3분 → 제작 비용 3분.

### 기체와 인물: 생성 뒤에 남는 일

프로젝트 기록에는 기존 AI 3D 모델을 Meshy 모델로 교체하고, Jenny·DH-4·Mailwing의 크기와 카메라 배율을 확인한 과정이 있다. 인물과 새도 교체 기록이 있다. 도구별 우열을 단정하지 않고 이 프로젝트에서 실제로 확인한 작업을 설명한다.

생성 모델 → 형태 선택 → 크기·축·피벗 확인 → 재질·충돌·가동부 확인 → 엔진 배치 → 실제 카메라로 확인의 순서로 보여준다. 모델 이미지 한 장이 좋아 보여도 프로펠러 회전, 조종면, 시야, 성능은 게임 안에서 확인해야 한다.

### 대표 실패·수정 사례: 붓 줄기에서 날리는 눈발로

베타 아트 기록에는 고개 바람을 흰 붓 줄기로 표현했다가 “세게 불어오는 바람 같지가 않아”라는 평가로 날리는 눈발로 교체한 사례가 있다.

두 영상을 같은 구간·비슷한 시점으로 비교한다. 질문은 ‘예쁜가?’와 함께 ‘바람의 방향과 세기를 읽을 수 있는가?’다. 시각적 효과의 채택 기준을 핵심 플레이와 연결한다.

강의용 수정 요청:

```text
고개에서 부는 바람이 현재 붓 줄기로는 약하게 느껴진다.
플레이어가 바람의 방향과 강도를 알아볼 수 있도록
날리는 눈발 표현을 조정해 줘.
바람의 물리 규칙은 유지하고 시각 표현을 대상으로 작업해 줘.
같은 구간과 카메라에서 수정 전후를 비교할 자료를 남겨 줘.
```

### 서사와 소리

편지 초안과 번역은 인물의 말투·알고 있는 사실·분량·금지할 감정 표현을 먼저 정해 요청한다. 예를 들어 리브의 상실을 매 장면 직접 설명하지 않고, 사물과 행동의 여백으로 남기는 시놉시스 규칙을 적용한다. 작성한 문장을 실제 편지 화면에서 읽어보고 줄 길이와 읽는 시간을 확인한다.

사운드는 엔진·바람·우편 전달이 서로 묻히지 않는지, 반복음이 피곤하지 않은지 듣는다. 프로젝트에는 코드 합성 소리와 외부 소리 교체 기록이 있으며, 출처 확인이 남은 소리도 있다. 출처가 확인되지 않은 항목을 상업 이용 가능하다고 소개하지 않는다.

### 1인 개발의 비용 판단

생성 버튼을 누르는 시간 외에 후보 선별·보정·엔진 통합·재검증 시간을 합친다. 비용표는 ‘도구/에셋, 결제액, 채택한 결과, 통합 시간, 재작업 시간’으로 기록한다. 실제 결제 자료가 없으므로 총 개발비·절감률을 만들어 넣지 않는다.

발표 멘트:

> “후보를 많이 만드는 것과 게임에 쓸 결과 하나를 완성하는 것은 작업량이 다릅니다. 저는 실제 화면에서 쓸 수 있는지, 다른 에셋과 어울리는지, 다음 수정이 가능한지까지 보고 채택해야 합니다.”

## 5. 완성 — 하루의 흐름부터 제품 기능까지 (15분)

진행: 진행 연결 5분 → 개발 단계 3분 → 제품 기능 5분 → 동결 기준 2분.

Wind Courier의 흐름을 ‘타이틀 → 아침 카운터 → 노선·편지 선택 → 비행 → 투하/착륙 전달 → 귀환 → 저녁 → 저장 → 다음 날 → 엔딩’으로 설명한다. 실제 촬영 영상은 촬영 시점의 구현 상태와 일치시킨다.

### 단계마다 끝내야 할 일이 다르다

| 단계 | Wind Courier에서 확인할 질문 |
|---|---|
| 프로토타입 | 바람을 읽으며 날고 배달하는 행동을 계속하고 싶은가? |
| 버티컬 슬라이스 | 짧은 한 구간에서 목표 화면·소리·조작 경험을 확인했는가? |
| 알파 | 주요 기능이 연결되어 처음부터 엔딩까지 진행할 수 있는가? |
| 베타 | 정한 콘텐츠를 채우고 새 기능을 멈춰 다듬는 단계인가? |
| 출시 후보 | 이 빌드를 고객에게 전달해도 되는가? |

이는 강의에서 사용할 단계의 기준이다. 모든 단계를 순서대로 별도 빌드로 완료했다는 개발 이력을 뜻하지 않는다.

### 실제 출시 준비 문서에서 발견한 일

- 타이틀, 일시정지, 설정, 조작 안내, 크레딧.
- 저장 실패·손상 대비와 백업 복구.
- 한국어·영어 문장과 화면 넘침.
- 메뉴까지 포함한 게임패드 조작.
- 해상도·화면비·그래픽 품질·접근성.
- Shipping 빌드에서 개발용 입력·진단·기록을 정리하는 작업.

기록에는 이 항목들의 구현·자동 확인과 별도로, 사람의 전체 플레이 확인이 남아 있다. ‘설정 화면이 존재한다’와 ‘설정 변경 후 재시작해도 유지된다’를 다른 완료 조건으로 보여준다.

AI에는 누락 목록 작성, 반복되는 UI·설정 구현, 번역 일관성 확인, 빌드 절차 정리를 맡길 수 있다. 사람은 전체 플레이 흐름과 실제 장치에서의 사용성을 확인한다.

발표 멘트:

> “처음에는 비행을 만드는 일이 크게 보였습니다. 출시 준비표를 보면 종료, 저장, 글자 크기, 패드 메뉴 같은 일도 남아 있습니다. 플레이어가 게임을 시작하고 끝낼 때까지의 경험을 완성해야 합니다.”

## 6. 검증 — AI의 완료 보고를 확인하는 방법 (15분)

진행: 기록 읽기 4분 → 전후 비교 4분 → 버그 요청 4분 → 청중 활동 3분.

### 같은 ‘성공’도 뜻이 다르다

| 확인 | 알 수 있는 것 | 별도 확인할 것 |
|---|---|---|
| 컴파일 성공 | 코드가 빌드된다 | 실제 진행·재미·시야 |
| 자동 검사 통과 | 검사한 조건에서 규칙이 맞는다 | 검사하지 않은 상황 |
| 자동 경로 완료 | 정해진 경로의 상태 전환이 작동한다 | 초보자의 길 찾기와 조작 |
| 화면 캡처 확인 | 해당 화면의 배치와 가독성 | 움직임·피로·장시간 플레이 |
| 사람 플레이 | 경험·이해·불편을 관찰한다 | 다른 환경과 반복 상황 |

실제 측정 기록 사례: 2026-09-19 자동 경로 검사에서 30/60/120 FPS 조건의 배달 경로 완료와 고도 회복이 기록되어 있다. 기록 자체에 사람의 재미·입력 피로도는 미검증이라고 명시되어 있다. 이 구분을 그대로 설명한다.

성능표에는 빌드, 장면, 해상도, 그래픽 설정, 하드웨어, 측정 구간을 함께 적는다. 개발 PC에서의 수치를 최소 사양의 근거로 바로 바꾸지 않는다.

### 실제 UI 사례: 연료 게이지 위치 조정

베타 기록에서 연료 게이지를 왼쪽 위, 오른쪽 아래, 아래 가운데 등으로 조정한 과정을 보여준다. 그 과정에서 자동 검사가 통과해도 위치에 대한 사람의 평가가 다시 필요했다는 점을 설명한다. 단계별 화면이 없으면 문서의 변경 기록을 사용하고, 과거 화면을 임의로 재현해 실제 캡처처럼 제시하지 않는다.

### 버그 수정 요청의 구조

```text
Wind Courier의 [빌드 번호]에서 다음 문제가 발생했다.
환경: [해상도 / 언어 / 입력 장치]
재현: [시작 상태] → [행동] → [문제]
기대: [원하는 동작]
실제: [관찰한 동작]
첨부: [로그 / 화면 / 세이브 복사본]

원인 후보를 근거와 함께 좁히고 관련 부분을 수정해 줘.
동일 조건의 재검사와 영향을 받는 기존 동작을 확인해 줘.
재현하지 못했다면 재현하지 못했다고 기록해 줘.
```

청중 활동: ‘전체 패드 지원’, ‘저사양에서도 실행’, ‘상승기류가 재미있다’ 중 자동 검사만으로 확정할 수 있는 항목을 묻는다. 모두 추가 관찰이 필요함을 설명한다. 지원 문구는 확인 결과와 맞춰 쓴다.

## 7. Steam — 상점부터 출시 후 첫 대응까지 (17분)

진행: 상점·홍보 4분 → 제출·일정 5분 → AI·에셋 기록 3분 → 출시 당일·초기 운영 5분.

이 부분은 Wind Courier가 앞으로 완료할 출시 작업이다. 상점 초안과 출시 준비표는 있지만 출시 성공 사례나 판매 수치는 제시하지 않는다. 강의 구조에서는 마지막 장이지만 실제 상점 준비는 개발 중에 병행한다.

### Wind Courier를 플레이어에게 설명하기

상점 소개는 ‘작은 복엽기로 바람을 읽고, 마을에 우편을 투하하고, 중요한 편지를 직접 전하는 저속 비행 어드벤처’로 시작한다. 리브와 아버지의 우편 가방은 행동을 이해한 뒤 이야기의 동기로 연결한다.

영상 구성 예시: 바람을 타는 비행 → 저공 투하 → 착륙 전달 → 편지와 인물 → 하루의 귀환. 이 순서는 강의용 편집 제안이며 기존 트레일러가 있다는 뜻은 아니다. 상점 이미지와 영상은 실제 플레이를 중심으로 준비한다.

AI에는 소개문 길이 조절, 한국어·영어 초안, 촬영 목록, 개발일지 초안을 맡긴다. 사람이 구현 여부와 표현을 대조한다. 현재 상점 초안의 전체 패드 지원·플레이 시간·사양은 사람 확인 목록과 맞춰 재검토할 사례로 쓴다.

홍보 소재는 ‘바람 표현 수정 전후’, ‘기체가 실제 게임에 들어오는 과정’, ‘첫 우편 배달’처럼 플레이의 차이를 보여주는 짧은 영상으로 준비한다. 공개 후에는 조회수와 함께 상점 방문·위시리스트·데모 피드백을 보고 다음 소재를 조정한다. 특정 수치를 성공의 보장으로 제시하지 않는다.

### 제출과 일정

1. Steamworks 등록, 신원·은행·세금 정보와 계약 절차를 준비한다.
2. 앱 등록비, 상점 자료, 가격, 지원 언어·기능을 준비한다.
3. 상점 검토를 제출하고 승인 후 Coming Soon을 공개한다.
4. 배포 파일 묶음인 Depot과 실행 설정을 구성하고, 빌드를 올려 Steam에서 설치·실행을 확인한다.
5. 상점에 소개한 기능이 포함된 출시 후보 빌드의 검토를 받는다.
6. 승인·대기 조건·최종 점검을 충족한 뒤 실제 출시 절차를 수행한다.

Steam은 상점과 빌드 체크리스트를 별도로 운영하고, 상점 검토 제출을 빌드 검토보다 먼저 하도록 안내한다. 승인 자체와 실제 출시는 구분된다. 출처: [Steam Release Process](https://partner.steamgames.com/doc/store/releasing).

2026-10-03 열람한 온보딩 본문은 초기 타이틀의 앱 수수료 결제 후 대기를 **21일**, Coming Soon 공개를 **최소 2주**로 안내한다. 검색 결과의 과거 30일 안내와 차이가 있으므로 강의 직전에 공식 본문과 실제 앱 화면을 재확인한다. 이 기간만 확보하면 신원 확인·심사·수정까지 모두 끝난다는 뜻은 아니다. 출처: [Steam Onboarding](https://partner.steamgames.com/doc/gettingstarted/onboarding).

앱당 등록비는 100 USD 또는 해당 지역의 동등 금액이며, 환불 대신 정해진 매출 조건을 충족하면 정산에서 회수되는 구조다. 출처: [Steam Direct Fee](https://partner.steamgames.com/doc/gettingstarted/appfee).

### AI 사용과 외부 에셋 기록

Steam의 현재 설문은 플레이어가 접하는 아트·소리·서사·번역 등의 AI 콘텐츠를 다루며, 개발 중 사전 생성과 실행 중 생성을 구분한다. 실행 중 생성에는 불법 콘텐츠 생성을 막는 조치 설명이 추가된다. 생산성 도구 사용과 출하되는 AI 콘텐츠를 구분해서 실제 사용 내역대로 답한다. 출처: [Steam Content Survey](https://partner.steamgames.com/doc/gettingstarted/contentsurvey).

Wind Courier에서는 최종 빌드에 포함된 3D 모델, 글·번역, 소리의 출처와 생성 방식을 목록화한 뒤 제출 문구를 만든다. ‘AI 사용’이라는 한 줄만 적지 말고 무엇에 어떻게 사용했는지 확인한다.

에셋 기록 양식: 파일/게임 내 용도/제작자 또는 서비스/다운로드·생성일/당시 요금제/라이선스 원문/필요 표기/최종 포함 여부. 프로젝트에 남은 Meshy 요금제 및 소리 출처 확인 항목을 실제 사례로 보여준다. 이용 조건이 확인되지 않은 에셋은 확인하거나 출처가 명확한 대체물로 바꾼다.

### 출시 당일과 이후

| 시점 | Wind Courier에서 할 일 | AI의 보조 작업 |
|---|---|---|
| 출시 전 | 출시 후보 버전 보관, 새 설치·이어하기·설정·엔딩 점검, 상점 문구 대조 | 체크리스트와 검사 결과 정리 |
| 출시 당일 | 판매·다운로드·설치·실행 확인, 문의 경로 확인 | 문의 분류와 재현 정보 양식 작성 |
| 초기 대응 | 실행 불가·저장 손상·진행 불가부터 우선 처리 | 로그 정리, 원인 후보, 수정·회귀 확인 |
| 패치 배포 | 이전 세이브와 호환 확인 후 패치, 변경 내용 공지 | 실제 수정 사항에 근거한 패치 노트 초안 |

출시용 인증정보는 공개 시연에 노출하지 않는다. 패치 전에는 이전 빌드와 세이브 호환을 확인하고 복구 가능한 버전을 보관한다. 고객에게 전달하는 약속과 공개 문구는 개발자가 검토한다.

발표 멘트:

> “Wind Courier의 출시 준비는 상점에 적은 경험과 실제 빌드가 일치하는지 확인하는 과정입니다. 게임이 판매된 다음에는 처음 실행하는 사람의 문제를 수집하고, 재현하고, 고치는 흐름까지 이어집니다.”

## 8. 정리와 질의응답 (10분)

정리 2분, 질의응답 8분. 질문이 적으면 아래 질문을 사용한다.

마지막 발표 멘트:

> “Wind Courier에서 가져가실 작업 방식은 네 가지입니다. 만들 경험을 한 문장으로 정하기, AI 작업에 확인 가능한 완료 조건 붙이기, 게임 안에서 직접 확인하기, 다음 작업을 위해 결정과 근거 남기기입니다. 여러분의 첫 작업은 게임 전체를 요청하는 대신 핵심 행동 한 가지를 정하고 그 행동이 되는지 확인하는 것입니다.”

예상 질문과 답변 방향:

- **코딩을 몰라도 가능한가?** AI가 구현을 도와도 실행·오류 재현·변경 확인·복구는 익혀야 한다. Wind Courier처럼 엔진과 게임 규칙이 결합된 프로젝트는 작은 동작을 이해하며 넓혀 간다.
- **AI를 쓰면 얼마나 빨라지는가?** 실제 비교 기록 없이 배수를 말하지 않는다. 생성 시간에 통합·수정·검증 시간을 더해 판단한다.
- **모든 에셋을 AI로 만들 필요가 있는가?** 장면의 일관성, 수정 가능성, 출처, 실제 제작 비용을 기준으로 직접 제작·기성 에셋·AI 결과를 선택한다.
- **AI가 끝났다고 하면 믿어도 되는가?** 완료 조건과 증거를 확인한다. 자동 검사 결과와 사람의 전체 플레이를 구분한 Wind Courier 기록을 다시 보여준다.
- **언제 출시할 수 있는가?** 목표 기능·콘텐츠, 제품 안정성, 외부 환경 확인, 상점·빌드 승인과 일정 조건을 충족했을 때 판단한다.

## 발표 전 준비

- 현재 플레이 영상 2분, 첫 투하 흐름 영상, 바람 표현 전후, 기체·UI 비교 자료를 확보한다.
- 영상마다 빌드 시점과 상태를 적는다. 과거 원본이 없으면 문서 기록으로 설명한다.
- 시연용 빌드와 세이브 복사본, 녹화본을 별도로 준비한다. 라이브 생성·빌드가 지연되면 녹화본으로 전환한다.
- 강의 직전에 Steam 정책·화면, 현재 출시 상태, 채택 에셋 목록을 다시 확인한다.
- 실제 출시 후에는 23~25장의 계획 자료를 검수 피드백·상점 화면·실제 배포와 패치 기록으로 갱신한다.
- 개발 시간·AI 비용·판매량은 근거 자료가 확보된 경우에만 넣는다.

## 수강생 배포용 — 내 프로젝트에 적용하기

수업 중 두 번의 3분 활동에서 아래 1·2번을 작성하고, 마지막 정리에서 3번의 다음 행동을 정한다. 추가 수업 시간은 배정하지 않는다. 나머지는 수업 후 자신의 프로젝트에 적용한다.

### 1. 컨셉과 첫 검증 범위

- 내 게임은 플레이어가 ______하면서 ______을 느끼는 게임이다.
- 가장 자주 반복하는 행동은 ______이다.
- 첫 프로토타입에서 만들 세 가지는 ______ / ______ / ______이다.
- 이번에 만들지 않을 것은 ______이다.
- 재미를 확인하려면 플레이어에게 ______을 시켜보고 ______을 관찰한다.

Wind Courier 예시: 바람을 읽으며 편지를 배달한다. 비행·기류·투하부터 만들고, 전체 이야기와 정교한 마을은 뒤로 미룬다. 기류를 찾고 투하 후 다시 고도를 회복하는 과정을 관찰한다.

### 2. AI에 맡길 작업 한 장

```text
참고할 문서와 파일:
현재 가능한 동작:
이번에 바꿀 동작 한 가지:
완료 조건:
  - 정상 상황:
  - 실패 상황:
  - 반복 입력 또는 재시작 상황:
확인할 증거:
사람이 직접 확인할 항목:
```

작성 예: 투하 조건 밖에서는 편지를 보존하고, 성공하면 한 번만 배달을 완료한다. 같은 편지를 다시 투하해도 중복 완료되지 않는지 검사한다. 접근할 때 투하 가능 상태를 알아볼 수 있는지는 직접 플레이한다.

### 3. 출시까지 남은 일

| 질문 | 내 프로젝트의 답 |
|---|---|
| 처음부터 끝까지 진행 가능한가? | |
| 새 설치와 저장 후 재실행을 확인했는가? | |
| 다른 사람이 설명 없이 플레이했는가? | |
| 상점에서 약속할 기능을 실제로 확인했는가? | |
| 최종 에셋의 출처와 AI 사용 내역이 정리됐는가? | |
| 상점 준비와 빌드 검토 일정이 개발 일정에 포함됐는가? | |
| 다음 작업 한 가지와 완료 조건은 무엇인가? | |

## 강사용 질문과 피드백 기준

| 구간 | 던질 질문 | 답변에서 확인할 것 |
|---|---|---|
| 컨셉 | “바람을 읽는다는 것을 어떤 조작과 화면으로 확인할까요?” | 감정·설정에서 관찰 가능한 행동으로 내려오는가 |
| 프로토타입 | “AI가 투하 구현을 마쳤다고 하면 무엇을 해볼까요?” | 성공뿐 아니라 실패·재시도·중복 입력도 제시하는가 |
| 아트 | “바람 표현 두 개 중 무엇을 채택할까요?” | 화면의 아름다움과 방향·강도의 전달을 함께 판단하는가 |
| 완성 | “설정 화면을 만들면 설정 기능은 완료일까요?” | 적용·재시작 후 유지·다른 해상도를 확인하는가 |
| 검증 | “자동 경로가 끝났으면 초보자도 엔딩을 볼 수 있을까요?” | 자동 진행과 사람의 이해·조작을 구분하는가 |
| 출시 | “상점에 전체 패드 지원을 쓰려면 어디까지 확인할까요?” | 비행 외에 메뉴·편지·설정·엔딩까지 확인하는가 |

강사는 정답 도구 이름보다 작업 범위와 확인 방법을 구체적으로 말하는지 평가한다. 수강생이 “AI에게 게임을 만들어 달라고 한다”라고 답하면 “첫 번째로 확인할 동작 하나는 무엇인가요?”로 좁힌다.
